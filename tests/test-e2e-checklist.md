## Notes / false positives seen

No false positives in the final runs. What the earlier passes exposed, each
fixed with a failing test first:

1. Pass 1 counted test and Markdown lines in the coverage TOTAL (clean showed
   85/85) and showed a never-loaded file as 0/0. Coverage now counts only
   changed source files, and a file with no lcov record is listed as
   `NO_RECORD` with all its added lines, named in the Tools line and the SDD
   block, and kept out of TOTAL.
2. Pass 1 on `clean`: the correctness reviewer flagged the fixture's SQL
   column `user`, a reserved word in PostgreSQL. Correct finding; the
   fixtures now use `user_id`.
3. Pass 1 on `dirty` printed `?` as the function of statement-level metric
   rows, and with a baseline one old `max-depth` or magic number hid every
   new one in the same file. Nameless rows are now matched across trees by
   their source line, and the function column says `-` or `(anonymous)`.
4. Pass 2 on `clean` returned REQUEST CHANGES with one BLOCKER, correctly:
   after the `user_id` rename the listing returned raw rows, not the spec's
   `{id, user, qty}`. The fixture now maps rows to the contract; pass 3
   approves.
5. Pass 2 on `dirty`: the verifier merged 32 raw findings into 19, folding
   distinct defects together (`eslint-disable` into the SQL injection, the
   duplication row into the `NO_RECORD` blocker, the complexity, length and
   depth rows into cognitive complexity). Dedup now merges only findings with
   one root cause and never merges different rule-based rows; the same input
   re-verified to the 26 findings above, every seed with its own entry.
6. The 32 findings (29 KB) were too many to paste into one verifier prompt;
   verifiers now read their group from `$WORK/verify-<n>.json`.
